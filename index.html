How the verdict is decided
Every failing component is mapped to its pages and those pages are added to coverage (union with the pages that fail directly). A criterion is Does Not Support if a blocker is present anywhere, OR that page union covers more than 50% of in-scope pages. Otherwise, any finding caps at Partially Supports. No component severity/criticality is used in the math — every failing component contributes its full mapped pages.
How to use this tool
  1. Pick your WCAG target (version + level) below. This defines the full set of success criteria your VPAT covers, so the tool can count Supports and Not Applicable, not just failures.
  2. Set the true page count. Pages with zero issues never appear in the CSV, so by default the denominator only counts pages that have findings — which inflates Coverage %. Enter Total pages in scope, or paste the full page list, so percentages use the real denominator.
  3. Upload one or more CSV exports from axe Auditor. Drag them onto the box or click to browse. Add files from different platforms (web, iOS, Android…) — they are merged cumulatively: a page that fails a criterion on any platform is counted as failing.
  4. Map each shared component to its pages (do this first — it decides the verdict). For every component the audit found (header, footer, nav, widgets…), click Global (all pages) or tick the exact pages it sits on. Every failing component's mapped pages are unioned into Coverage %, so an unmapped or under-mapped component silently undercounts coverage and can hide a Does Not Support verdict that should have fired.
  5. Handle project-wide pages (optional). If your audit logs application-wide issues on a dedicated project-wide / app-wide page, mark it in section 2b. It is dropped from the page count, and you map each of its issues to the real pages where they reproduce (or All pages). Those issues then count as direct page failures on the mapped pages — adding to Coverage just like any other page failure.
  6. Read the conformance table. Each criterion shows Coverage % = the union of directly-failing pages and every failing component’s mapped pages. The rule: Does Not Support if a blocker is present anywhere, or that page union covers more than 50% of in-scope pages. Everything else with findings is Partially Supports; nothing found is Supports. Component severity is not used — every failing component adds its full mapped pages. Because components are unioned into coverage, mapping each component to its real pages (section 2) directly affects the verdict.
  7. Override a verdict in the last column when needed: Not Applicable where a criterion does not apply, and (for WCAG AAA criteria only, per ITI rules) Not Evaluated or Supports. AAA criteria with no findings default to Not Evaluated.
  8. Draft remarks. On any Partially Supports / Does Not Support row, click Remarks to generate ITI-style "Remarks & Explanations" text listing the affected components and pages — edit it before pasting into your ACR.
  9. Export CSV to drop the results straight into your VPAT. Nothing is stored in this browser \u2014 refreshing the page or clicking Start new VPAT gives a completely clean slate, so one VPAT's data never leaks into the next. Export your CSV before closing the tab.

2b. Project-wide / app-wide pages

What is this, and when do I use it?

Sometimes an audit includes a deliberate project-wide / app-wide page — a container used to log issues that are common across the whole application rather than tied to one screen. Such a page is not a real screen, so counting it as one would distort the page total and Coverage %.

Mark that page below. The tool will (1) remove it from the in-scope page count, but (2) keep its issues. Then you see every individual issue logged on that page (by issue ID, with its description, severity and success criteria) — because one criterion can have several distinct issues that reproduce on different screens. For each issue, tick the real pages where it reproduces — or click All pages if it affects the whole product. Each redistributed issue applies all of its success criteria to the pages you mapped it to and is counted as a direct page failure there, so it adds to Coverage and can drive the verdict exactly as a normal page failure would (a blocker still forces Does Not Support). Issues you leave unmapped are not counted.

How the verdict is decided. Does Not Support if (1) a blocker issue is present anywhere, or (2) the union of directly-failing pages and every failing component’s mapped pages covers more than 50% of in-scope pages. Coverage % here is that page union. Component severity/criticality is not used: every failing component contributes its full mapped pages, and a union at or below 50% (with no blocker) keeps the criterion at Partially Supports. For pages + components we take the page union, deduped. No findings is Supports. Project-wide pages are excluded from the count; their issues redistribute to mapped pages as direct failures.
